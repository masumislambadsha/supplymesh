# Deliverable 03 — API Structure Proposal

> Scope: the public HTTP contract of the SupplyMesh `api` container. Table, column, status and enum names come from [`schema.sql`](../02-database/schema.sql). The architecture behind the API (modules, guards, transactions) is in [application-architecture.md](application-architecture.md). The four critical workflows are traced end to end in [system-design.md](../04-system-design/system-design.md).

## 1. Principles

| # | Principle | Decision | Why (SupplyMesh-specific) | Alternative considered |
|---|---|---|---|---|
| P1 | Style | **REST over JSON**, resource-oriented, plural nouns (`/suppliers`, `/purchase-orders`) | The domain is a set of documents (request, PO, invoice) with clear lifecycles, which maps naturally onto resources. HTTP caching semantics, status codes and `ETag` support optimistic locking without extra tooling. | **GraphQL**: flexible reads for dashboards, but per-field authorization, query-cost limits and idempotent mutations would all have to be built by hand. Analytics needs are covered by purpose-built endpoints. **tRPC**: tightly couples web and api and gives no language-neutral contract for future ERP integrations. |
| P2 | State transitions | **Action sub-resources**: `POST /purchase-requests/{id}/submit`, `POST /purchase-orders/{id}/issue` | Each transition has its own permission, preconditions, audit action and outbox event. `PATCH {"status":"approved"}` would hide all of that behind one generic endpoint and invite mass-assignment of `status`. | Generic `PATCH` of `status`: fewer endpoints, but authorization becomes a large switch statement and the OpenAPI contract stops documenting the workflow. |
| P3 | Base path and versioning | `/api/v1`. **Major version in the URL**, additive changes inside a version. | Simple to route in NGINX and the ALB, visible in logs, and easy for customers' integration teams to pin. | Header or media-type versioning (`Accept: application/vnd.supplymesh.v2+json`): cleaner URLs, but harder to test with curl and to route at the proxy. |
| P4 | Naming in JSON | **snake_case** for every field, query parameter and filter (`purchase_request_id`, `estimated_total_base`, `?department_id=`, `next_cursor`) | Field names then match `schema.sql` columns one-to-one, so the docs, the audit `before_data`/`after_data`, CSV exports and the API all use the same names. Filters and sort keys (`sort=-created_at`) are column names. Support engineers can move from a log line to SQL without translating names. | **camelCase**: idiomatic in TypeScript. The trade-off is that zod contracts in `packages/contracts` define snake_case properties, so frontend code reads `request.estimated_total`. We accept that; Drizzle column names already map to snake_case, so no mapping layer is needed in the backend. |
| P5 | Contract | OpenAPI 3.1 document generated by `@nestjs/swagger` from controller decorators. Request and response DTOs are derived from **zod schemas in `packages/contracts`**, which the Next.js app imports for form validation. | One source of truth for validation on both sides. CI fails when the generated spec changes in a breaking way (a breaking-change diff check runs on every PR). | Hand-written OpenAPI YAML: drifts from the code. Code-first without shared zod: client and server validation would diverge. |
| P6 | Money and time | Amounts are **decimal strings** (`"2592.0000"`), never JSON numbers. Currency is ISO 4217 (`"EUR"`). Dates are `YYYY-MM-DD`; timestamps are RFC 3339 in UTC (`2026-11-12T09:15:02Z`). IDs are UUIDv7 strings. | `NUMERIC(19,4)` can't be represented exactly in an IEEE-754 double, and JavaScript would silently round. Decimal strings map to the `Money` value object. | JSON numbers: shorter, but loses precision on large amounts. Integer minor units: currencies differ in decimal places (JPY 0, KWD 3), and the schema already uses 4 decimal places. |
| P7 | Tenancy | **The tenant always comes from the access token** (`org_id` claim). No organization id appears in any URL, path or body (one exception: `POST /auth/switch-organization`, which names the target membership and is verified against `organization_members`). | Prevents IDOR across tenants by construction. Resource ids are globally unique UUIDs, and RLS returns no row for another tenant's id, so the response is `404`, which does not reveal that the id exists. | `/orgs/{orgId}/...` paths: readable, but every handler must then compare the path with the token, and one missed comparison is a data leak. |

### 1.1 Versioning and deprecation policy
- **Non-breaking (same version):** new endpoints, new optional request fields, new response fields, new enum values in fields documented as "extensible" (for example `notifications.type`). Clients must ignore unknown fields.
- **Breaking (new major version):** removing or renaming a field, changing a type, making an optional field required, changing the meaning of a status value, or tightening validation of existing data.
- A deprecated endpoint or field is marked `deprecated: true` in OpenAPI and its responses carry `Deprecation` and `Sunset` headers plus a `Link: <…>; rel="deprecation"` to the migration note.
- `/api/v1` and `/api/v2` run side by side for at least **6 months** after `v2` is released. Both versions are served by the same modular monolith (a thin controller layer per version over the same use cases), so there is no second deployment to run.
- The web app always uses the newest version. The version policy exists for future customer integrations (ERP export, webhooks), which are Future scope (§10).

## 2. Request conventions

### 2.1 Headers

| Header | Direction | Required | Purpose |
|---|---|---|---|
| `Cookie: access_token=…` or `Authorization: Bearer <access JWT>` | request | Every endpoint except `/auth/login`, `/auth/mfa/verify`, `/auth/refresh`, `/auth/signup`, password reset, and `/public/*` | RS256 JWT, 15 minutes. Claims: `sub` (user_id), `org_id`, `member_id`, `sid` (session_id). **Permissions are not in the token**; they are loaded from Redis (`org:{orgId}:member:{memberId}:perms`, 10 min TTL, deleted on any role change). Browsers send it as an httpOnly, Secure, `SameSite=Lax` cookie set at login; the Next.js server and future machine clients send the same JWT as a bearer header. |
| `Cookie: refresh_token=…` | request | `/auth/refresh`, `/auth/logout` only | Opaque, 14 days, rotated on every use, `httpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. The browser never exposes it to JavaScript. |
| `Origin` | request | Every `POST`, `PUT`, `PATCH`, `DELETE` sent by a browser | Must equal the web origin, otherwise `403`. CSRF defence, because cookies are sent automatically (§8). |
| `Content-Type: application/json` | request | Bodies | Anything else → `415` (rare; listed with 400 in §4) |
| `Idempotency-Key: <uuid>` | request | **Required** on `POST /payments`, `POST /purchase-orders/{id}/issue`, `POST /invoices` (and `POST /invoices/bulk`). **Accepted** on every other `POST`. | See §2.3 |
| `If-Match: "<version>"` | request | **Required** on `PATCH` and state-changing actions of the four versioned resources: suppliers, purchase requests, purchase orders, invoices | Optimistic locking (§2.4). Missing → `428`, stale → `412`. |
| `X-Request-Id: <uuid>` | both | Optional on request | If the client (or NGINX) sends one, it is reused. Otherwise the API generates a UUIDv7. It is echoed in the response, written to every log line, put on every `audit_logs.request_id`, and included in every problem response. |
| `ETag: "<version>"` | response | On single-resource reads and writes of versioned resources | The row's `version` column |
| `Location` | response | `201` and `202` | URL of the created resource or of the async job |
| `Idempotent-Replayed: true` | response | When a stored response is replayed | Lets the client tell a replay from a first execution |
| `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset`, `Retry-After` | response | Always / on `429` | §8 |
| `Cache-Control: no-store` | response | All `/api/v1` responses | Financial data must not be cached by browsers or proxies |

### 2.2 Guard chain and the order of checks
Every request passes the same pipeline. The order matters because it decides which status code a client sees when several things are wrong at once.

1. NGINX: TLS, per-IP rate limit, body size limit (§8) → `429` / `413`
2. `JwtAuthGuard`: access JWT from the cookie or the bearer header, valid signature, not expired → `401`. On state-changing requests the `Origin` header must equal the web origin → `403`
3. `TenantContextGuard`: the membership in `org_id` exists and is `active`; sets AsyncLocalStorage tenant context → `401` (membership gone) 
4. `ThrottlerGuard`: per-member rate limit in Redis → `429`
5. `PermissionGuard`: `@RequirePermission('invoice.approve')` → `403 forbidden`
6. `ValidationPipe` (zod contract, unknown fields rejected) → `400` / `422`
7. Idempotency interceptor (§2.3): replay or `409` while the first call is still running
8. Use case inside `withTenantTx(orgId, …)` (`SET LOCAL app.current_org_id`): load + lock the row (`404` if RLS hides it), compare `version` with `If-Match` (`428` / `412`), scope policy (department, own records → `404` or `403`), business policy (state machine → `409`, approval limit / segregation of duties → `403`, business-rule violation → `422`)
9. Audit row + outbox row in the same transaction, then `COMMIT`

### 2.3 Idempotency
- The client generates a UUID per **user intent** (for example, when the "Record payment" dialog opens), and reuses it for every retry of that intent.
- The interceptor stores `{fingerprint, status, body}` in Redis under `org:{orgId}:idem:{key}` for **24 hours**. The fingerprint is a SHA-256 of `member_id + method + route + canonical body`.
- Same key, same fingerprint, finished → the stored response is returned with `Idempotent-Replayed: true`. Same key, still running → `409 idempotency_in_progress`. Same key, different fingerprint → `422 idempotency_key_reused`.
- Missing on one of the three required endpoints → `400 idempotency_key_required`.
- **Redis is a convenience, not the guarantee.** Payments also insert `payments.idempotency_key` with `UNIQUE (organization_id, idempotency_key)` and `ON CONFLICT DO NOTHING`, so a retry returns the existing payment even if Redis was flushed. `POST /invoices` is protected by `UNIQUE (organization_id, supplier_id, supplier_invoice_number)`; `POST /purchase-orders/{id}/issue` is protected by the `draft → issued` state check under a row lock. If Redis is down, these endpoints still never execute twice; the only loss is that a retry gets `409` instead of the original `2xx` body.

### 2.4 Optimistic concurrency (`ETag` / `If-Match`)
- Only tables with a `version` column use it: `suppliers`, `purchase_requests`, `purchase_orders`, `invoices`. `ETag` is the strong value `"<version>"`.
- `PATCH` and state-changing actions on these resources require `If-Match`. Missing → `428 precondition_required`. Mismatch → `412 precondition_failed` with the current version in the problem body, so the UI can reload and show what changed.
- **Not covered:** approval decisions (protected by a row lock on the step plus `UNIQUE (approval_step_id, decided_by_member_id)`), payments (row lock on the invoice plus idempotency), and configuration resources without a `version` column (departments, roles, categories, workflow drafts), which are last-write-wins with every change audited. This is listed as a known limitation in the [Risk doc](../06-risk/risk-and-scalability.md#9-known-limitations-of-the-design).
- When a request also carries an `Idempotency-Key`, the idempotency lookup runs **first**, so a retried `issue` call is replayed rather than failing with `412` because the version has since moved on.

### 2.5 Pagination, filtering, sorting
| Concern | Convention | Example |
|---|---|---|
| Pagination | **Cursor (keyset)** only. `limit` default 25, max 100. `cursor` is an opaque, signed base64 token encoding the sort key values and `id` of the last row. | `GET /purchase-requests?limit=50&cursor=eyJjIjoi…` |
| Filtering | Equality on whitelisted columns; comma-separated values mean OR; range filters use `_from` / `_to` suffixes; `q` is a text search where supported (trigram on `suppliers.legal_name`) | `?status=submitted,in_approval&department_id=0193…&created_from=2026-10-01` |
| Sorting | `sort` with a whitelisted column, `-` for descending, one secondary key at most; `id` is always appended as the tie-breaker | `?sort=-created_at`, `?sort=due_date` |
| Totals | **Not returned** on list endpoints. `COUNT(*)` over a large tenant on every page is expensive. Counts come from purpose-built endpoints (`/notifications/unread-count`, `/analytics/pending-requests`). | |
| Field selection / sparse fieldsets / `include=` | **Out of scope.** Each endpoint returns a fixed, documented shape. Detail endpoints embed their lines (`items`), list endpoints return a summary shape. | |

Why cursor and not offset: offset pagination re-scans skipped rows (slow on deep pages of a tenant with 120,000 requests a year), and it shows duplicates or skips rows when new requests arrive between page loads, which is common in an approval inbox. Keyset pagination uses the composite `(organization_id, …, created_at DESC)` indexes directly. Trade-off: no "jump to page 37", which list UIs in this product do not need.

## 3. Response formats

### 3.1 Single resource
A single resource is returned as a plain JSON object (no wrapper), with `ETag` when it is versioned. Detail responses embed child lines (`items`) and small related summaries (for example `supplier: { id, legal_name, status }`).

### 3.2 Lists
```json
{
  "data": [
    { "id": "0193a1c2-5b7e-7c41-9d2a-6e3f1b8c4a01", "request_number": "PR-2026-000123", "status": "in_approval", "estimated_total_base": "2592.0000" }
  ],
  "page": { "next_cursor": "eyJjIjoiMjAyNi0xMS0xMlQwOToxNTowMloiLCJpIjoiMDE5M2ExYzIifQ", "limit": 25 }
}
```
`next_cursor` is `null` on the last page.

### 3.3 Async jobs (`202 Accepted`)
Long-running work (CSV exports, an audit export, a manual intelligence recompute) returns `202` with `Location: /api/v1/exports/{id}` and a body `{ "id": "…", "status": "queued" }`. The client polls `GET /exports/{id}` until `status` is `completed` (with a 5-minute presigned `download_url`) or `failed`.

### 3.4 Errors: RFC 9457 `application/problem+json`
Every error has the same shape: `type`, `title`, `status`, `detail`, `instance`, `request_id`, and `errors[]` for field-level validation problems. Extension members carry machine-readable context. The last path segment of `type` is a stable snake_case code that clients can switch on. Stack traces and SQL never leave the server.

**409: duplicate invoice** (`POST /invoices`, caught by `UNIQUE (organization_id, supplier_id, supplier_invoice_number)`)
```json
{
  "type": "https://supplymesh.example/problems/duplicate_invoice",
  "title": "Duplicate supplier invoice",
  "status": 409,
  "detail": "Invoice INV-88341 from supplier SUP-00042 has already been recorded.",
  "instance": "/api/v1/invoices",
  "request_id": "0193a1d0-2f11-7a9b-8c3d-4e5f6a7b8c9d",
  "existing_invoice_id": "0193a0f7-9c2d-7e10-b4a5-1c2d3e4f5a6b",
  "existing_invoice_status": "approved"
}
```

**422: validation error** (`POST /purchase-requests`)
```json
{
  "type": "https://supplymesh.example/problems/validation_error",
  "title": "The request body is not valid",
  "status": 422,
  "detail": "2 fields failed validation.",
  "instance": "/api/v1/purchase-requests",
  "request_id": "0193a1d2-8a4b-7c3d-9e1f-2a3b4c5d6e7f",
  "errors": [
    { "pointer": "/items/0/quantity", "code": "too_small", "detail": "Must be greater than 0." },
    { "pointer": "/required_by_date", "code": "date_in_past", "detail": "Must be today or later." }
  ]
}
```

**403: segregation-of-duties violation** (`POST /invoices/{id}/approve` by the member who recorded the invoice, BR-20; `chk_inv_sod` is the database backstop)
```json
{
  "type": "https://supplymesh.example/problems/segregation_of_duties",
  "title": "Segregation of duties violation",
  "status": 403,
  "detail": "You recorded this invoice, so another member with invoice.approve must approve it.",
  "instance": "/api/v1/invoices/0193a0f7-9c2d-7e10-b4a5-1c2d3e4f5a6b/approve",
  "request_id": "0193a1d4-1b2c-7d3e-8f4a-5b6c7d8e9f01",
  "rule": "invoice_recorder_cannot_approve"
}
```

## 4. Status codes

| Code | Meaning in SupplyMesh | Typical endpoints |
|---|---|---|
| 200 OK | Read succeeded, or an action returned the updated resource | `GET` anything, `POST /purchase-requests/{id}/submit` |
| 201 Created | A new row was created; `Location` points at it | `POST /purchase-requests`, `POST /payments`, `POST /approval-steps/{id}/decisions` |
| 202 Accepted | Work queued for the worker; poll `Location` | `POST /analytics/exports`, `POST /supplier-intelligence/recompute` |
| 204 No Content | Success with nothing to return | `POST /auth/logout`, `POST /notifications/read-all`, `DELETE /invitations/{id}` |
| 400 Bad Request | The request can't be parsed, or a required header is missing (415 is used for a wrong content type) | Malformed JSON, missing `Idempotency-Key` |
| 401 Unauthorized | Not authenticated: missing/expired token, revoked session, inactive membership | Any protected endpoint |
| 403 Forbidden | Authenticated but not allowed: missing permission, SoD, approval limit | `POST /invoices/{id}/approve` by the recorder |
| 404 Not Found | Does not exist **for this caller**: unknown id, another tenant's id, outside department scope | `GET /purchase-orders/{id}` |
| 409 Conflict | Conflicts with current state: invalid transition, duplicate, idempotent request in progress | `POST /purchase-orders/{id}/cancel` after goods were received |
| 412 Precondition Failed | `If-Match` is stale | `PATCH /suppliers/{id}` |
| 422 Unprocessable Content | Well-formed but invalid: field validation or a business rule | Over-receipt, overpayment, policy gap |
| 428 Precondition Required | `If-Match` missing where it is mandatory | `POST /invoices/{id}/approve` without `If-Match` |
| 429 Too Many Requests | Rate limit; `Retry-After` set | Login attempts, public onboarding |
| 500 Internal Server Error | Bug or unexpected failure; alerted; `request_id` returned | — |

Also used where the standard requires them: `410 Gone` (public onboarding link expired or used), `413 Content Too Large` (body over the NGINX limit), `415 Unsupported Media Type`, `503 Service Unavailable`.

## 5. Endpoint catalog

All paths are relative to `/api/v1`. "Any member" means any authenticated active member, with no specific permission. Notes use the real enum values from `schema.sql`. **(I)** = `Idempotency-Key` required, **(V)** = `If-Match` required. Every state-changing endpoint writes an `audit_logs` row and, where noted, an outbox event.

| `POST /approval-delegations` | APR-08 out-of-office delegation | A `approval_delegations` table (member, delegate, from, to) |

Until then: an issued PO is changed by cancelling it (before receipt) and creating a new one, and an absent approver's step is moved with `/approval-steps/{id}/reassign`.

### 6.2 How the Owner and segregation of duties fit together
- **The Owner holds every permission except the transaction-execution set:** `purchase_order.create/update/issue/cancel/close`, `goods_receipt.create`, `invoice.create/match/approve/reject/void`, `invoice.resolve_discrepancy`, `payment.record`, `payment.manage`. The person who controls the rules should not also move goods and money (Feature Specification §2.2). A small organization can grant these to the Owner role explicitly; the grant is audited and every Owner is notified. Because a member can only grant permissions they hold themselves (§6.3), granting them to the Owner role needs a platform-level override that this design does not yet specify. This is listed as a known limitation in the Risk document.
- **Permissions are necessary, never sufficient.** Segregation-of-duties checks run in the domain service after the permission guard and apply to **everyone, the Owner included**:

| Rule | Enforced by | Error |
|---|---|---|
| A requester can't decide a step of their own request (BR-08) | Approval service; the engine also routes around the requester when steps are created | `403 segregation_of_duties` (`requester_cannot_approve`) |
| One vote per member per step | `UNIQUE (approval_step_id, decided_by_member_id)` | `409` |
| The invoice recorder can't approve it (BR-20) | Domain check + `chk_inv_sod` | `403` (`invoice_recorder_cannot_approve`) |
| The PO creator can't approve the invoice, record a payment for it, or complete a scheduled payment for it (BR-20) | Payables service, on `POST /invoices/{id}/approve`, `POST /payments` and `POST /payments/{id}/complete` | `403` (`po_creator_cannot_approve_or_pay`) |
| The member who changed bank details can't verify the supplier (BR-05) | Supplier service | `403` (`bank_change_needs_second_verifier`) |
| A member can't change their own role assignments | Access-control service | `403` (`cannot_modify_own_roles`) |

### 6.3 Guards against privilege escalation through custom roles
- `role.manage` and `role.assign` are Owner-only by default, and MFA is mandatory for Owners.
- A member can only grant permissions they hold themselves, and can't edit their own assignments.
- The Owner role can't lose `role.manage` / `role.assign`, and the last active Owner can't be removed.
- Every change to `role_permissions` or `member_roles` deletes the affected permission caches immediately, writes an audit row with before and after sets, and notifies all Owners.

What happens on retries:

| Situation | Result |
|---|---|
| Network timeout, the client resends the same key and body | `201` with the **same** body and `Idempotent-Replayed: true`. No second payment. |
| Redis was flushed in between | The insert hits `UNIQUE (organization_id, idempotency_key)` (`ON CONFLICT DO NOTHING`), and the existing payment is returned |
| Same key, different amount | `422 idempotency_key_reused` |
| A new key for an invoice that is already `paid` | `422 exceeds_outstanding` (`chk_inv_paid` is the backstop) |
| The caller created the purchase order behind this invoice | `403 segregation_of_duties` (`po_creator_cannot_approve_or_pay`) |

## 8. Security notes

| Concern | Control |
|---|---|
| Rate limits (starting values, tuned from metrics) | NGINX per IP: 20 req/s with a burst of 40 on `/api`; 10 req/min on `/auth/*` and `/public/*`. `@nestjs/throttler` per member with Redis counters: 600 reads/min, 120 writes/min; exports 10/hour per member. Login: 5 failed attempts per account per 15 min, then exponential lockout. Public onboarding: 30 requests per token per hour. `429` with `Retry-After` and `RateLimit-*` headers. |
| Payload size | `client_max_body_size 1m` on `/api`. Files never pass through the API: they go straight to S3 with a presigned PUT whose policy fixes content type and size (25 MB, also `chk_doc_size`). At most 200 lines per request, PO or invoice; string lengths follow the `VARCHAR` limits in the schema. |
| CORS | The web app and the API share one origin behind NGINX (`/` → web, `/api` → api), so CORS is **off** by default. If a separate origin is ever needed, it is an explicit allow-list, never `*` with credentials. |
| No tenant ids in URLs | The tenant comes from the token (§1, P7). Another tenant's ids return `404`. S3 keys and Redis keys are prefixed with the org id, and the API only signs keys under the caller's prefix. |
| Mass assignment | A global `ValidationPipe` with `whitelist: true` and `forbidNonWhitelisted: true`, and strict zod schemas: unknown fields → `422`. Server-controlled fields are never accepted from clients: `organization_id`, `status`, `version`, `*_number`, `*_base` amounts, `amount_paid`, `quantity_received`, `quantity_invoiced`, `approved_by_member_id`, `verified_*`, `recorded_by_member_id`. Status changes happen only through action endpoints. |
| Sensitive data in responses and logs | Bank details are masked except on the dedicated audited endpoint. Request logs redact `Authorization`, cookies, tokens in `/public/*` paths, `bank_details` and passwords. Tokens are never put in query strings. |
| Transport and headers | TLS 1.2+ at NGINX, HSTS, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, a strict Content-Security-Policy on the web app. |
| CSRF | Browsers attach the session cookies automatically, so every state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`) must carry an `Origin` header equal to the web origin, or it gets `403`. The access cookie is `SameSite=Lax`, which never rides on a cross-site `POST` but lets a deep link from an approval email arrive logged in. The refresh cookie is `SameSite=Strict` and path-scoped to `/api/v1/auth`. |
| Errors | No stack traces, SQL or internal ids of other tenants in problem responses. `404` instead of `403` for records outside the caller's tenant or scope. |
| Database role | The API connects as `supplymesh_app` (no `BYPASSRLS`, no UPDATE/DELETE on `audit_logs`), so even a compromised endpoint can't read another tenant or rewrite history. |

## 9. How the contract is produced and tested
- Controllers declare `@RequirePermission(...)`, `@ApiOkResponse(...)` and zod-derived DTOs. The OpenAPI document is generated at build time and published with each release.
- CI runs a breaking-change diff of the generated spec against `main`; a breaking change without a version bump fails the build.
- Contract tests in CI: for every endpoint, an integration test with a member of **another** organization expects `404`, and a member without the permission expects `403`. These two tests are generated from the route table, so a new endpoint can't be added without them.

## 10. Future scope: webhooks and outbound integrations
Not part of the MVP. Listed here so the current design does not block them.

| Capability | Design direction | Why it fits the current design |
|---|---|---|
| Outbound webhooks (`purchase_order.issued`, `invoice.approved`, `payment.completed`, …) | Per-org endpoint registrations, HMAC-SHA256 signatures, retries with backoff, delivery log | The events already exist in `outbox_events`; webhooks are one more consumer of the relay |
| ERP / accounting export (SAP, Oracle NetSuite, QuickBooks, Xero) | Push approved invoices and completed payments; pull GL codes and cost centers | Stable snake_case contract and versioning policy (§1.1) |
| Bank / payment execution | Payment files or bank APIs; this is where `processing` gets used | Payments are already a state machine with idempotency |
| Supplier portal API | Supplier users acknowledge POs and upload invoices themselves | Public onboarding already shows the token-scoped access pattern |
| SSO (SAML/OIDC) and SCIM provisioning | New ways to create sessions and memberships | The membership and permission model doesn't change |
| API keys for machine clients | Org-scoped service accounts with a restricted permission set | Same `PermissionGuard`; the tenant comes from the key instead of the JWT |
