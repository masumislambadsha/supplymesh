# ADR-004: Drizzle ORM for data access and migrations

- **Status:** Accepted · **Date:** 2026-11-12 · **Deciders:** Masum Islam Badsha
- **Related:** [ADR-001 PostgreSQL](ADR-001-postgresql-over-mongodb.md) · [ADR-003 Multi-tenancy](ADR-003-multi-tenancy.md) · [ADR-006 PO/invoice consistency](ADR-006-po-invoice-consistency.md) · [schema.sql](../02-database/schema.sql) · [Engineering practices](../07-engineering/engineering-practices.md)

## Context (the problem)

The backend is TypeScript (NestJS). It needs typed database access and versioned migrations for the schema in `schema.sql`. That schema relies on PostgreSQL features more than a typical CRUD app:

- composite tenant FKs on every child table, e.g. `(organization_id, purchase_order_id) → purchase_orders(organization_id, id)`;
- CHECK constraints that encode business rules (`chk_inv_paid`, `chk_poi_received`, `chk_inv_sod`, `chk_approver_target`);
- generated columns (`purchase_order_items.line_subtotal`, `purchase_request_items.line_total`);
- partial indexes for work queues (`idx_steps_pending_member … WHERE status = 'pending'`);
- RLS policies that read `app.current_org_id`, which must be set with `SET LOCAL` **inside the same transaction** as the queries;
- row locks (`SELECT … FOR UPDATE`) in payment, receipt and matching transactions (ADR-006).

## Decision drivers

- The TypeScript schema definition should express these constraints directly, so the migration diff reflects the real database.
- Tenant context must be set in the same transaction as every query, with minimal per-request overhead.
- Financial queries must be easy to read as SQL in code review (locks, aggregates, `ON CONFLICT`).
- Types must flow from the schema into `packages/contracts` without a code-generation step that can drift.
- Small API surface for a 3–6 person team; low runtime overhead in both `api` and `worker`.

## Options considered

| Option | How it would work here | Pros | Cons |
|---|---|---|---|
| **Drizzle ORM + drizzle-kit** | Tables defined in `packages/db` as TypeScript (`pgTable`), with `check()`, `generatedAlwaysAs()`, `index().where(sql…)`, composite `foreignKey()`, `pgPolicy` / `.enableRLS()`; queries via the SQL-like builder; `tx.execute(sql…)` for tenant context | SQL-first: the TS schema mirrors `schema.sql` almost 1:1; inferred types with no codegen; `.for('update')` row locks in the builder; thin runtime over node-postgres | Younger project with API changes between versions; relational query API less mature than Prisma's nested writes; smaller ecosystem |
| Prisma ORM 7 (current stable line) | `schema.prisma` models; Prisma Migrate; interactive `$transaction` with `$executeRaw` to set tenant context | Excellent developer experience and docs; Prisma Studio; mature migrations; large community. It has improved a lot: the v7 client runs without the Rust query engine and uses driver adapters such as `@prisma/adapter-pg`; TypedSQL gives typed raw queries; partial indexes arrived as a preview feature in 7.4. Composite FKs are supported through `@relation(fields, references)` | CHECK constraints and RLS policies are not part of the v7 schema, so they live in hand-edited migration SQL that the schema cannot show or diff. Row locks need raw SQL (`$queryRaw` / TypedSQL). Tenant context needs an interactive transaction or a client extension around each query |
| Prisma ORM 8 (release candidate at the time of writing) | A new "contract" (PSL or TypeScript builder) plus a SQL query builder | Closes most of the gap above: `@@check` constraints, `@@rls` with policy blocks, partial indexes with SQL predicates, and `forUpdate()` / `forNoKeyUpdate()` row locks in its query builder | A new major version with a new CLI and contract format; its API was still changing between release candidates. Adopting it now means building our money paths during a major-version transition |
| TypeORM | Decorated entity classes; repository pattern | Familiar in NestJS projects; OOP entities | Weaker type inference on query results; migration generation is less predictable; decorator metadata hides the SQL |
| Kysely (query builder only) | Hand-written SQL migrations; Kysely for typed queries | Very transparent SQL; excellent types | No schema definition, so types come from codegen against a live DB; we would build migration tooling ourselves |

## Decision

Use **Drizzle ORM** with the **node-postgres** `Pool` for queries, and **drizzle-kit** for migrations. The schema lives in `packages/db`. Every request and job runs in a helper:

```ts
withTenantTx(orgId, async (tx) => {
  // first statement of the transaction; set_config(..., true) is the
  // parameterizable form of SET LOCAL app.current_org_id
  await tx.execute(sql`select set_config('app.current_org_id', ${orgId}, true)`);
  return fn(tx);
});
```

Migrations are generated by drizzle-kit, reviewed as SQL in the pull request, and run from CI by the `supplymesh_migrator` role. Objects drizzle-kit does not generate (the partitioned `audit_logs` table and its monthly partitions, grants, any custom policy) are written as **custom SQL migrations** in the same migration history. This would be true with any ORM.

## Reasons for selection

1. **The schema is the specification, today, on a stable API.** CHECK constraints, generated columns, partial indexes, composite FKs and RLS are business rules in SupplyMesh. Drizzle declares all of them in the TypeScript schema, so a reviewer sees `chk_inv_paid` next to `amount_paid`. With Prisma 7 the CHECKs and RLS policies would exist only in hand-edited migration SQL. Prisma 8 can express them, but it is a release candidate with a new contract format; we do not want to build payment code on it during that transition.
2. **RLS context and queries share one transaction naturally.** In Drizzle, `db.transaction(tx => …)` gives one connection; the first statement sets `app.current_org_id`, and every repository receives `tx`. Prisma 7 can do the same with an interactive `$transaction` plus `$executeRaw`, or with a client extension that wraps each query in a batch transaction. Both work, but the extension pattern adds a statement per query.
3. **Transparent SQL for money.** Payment recording locks the invoice row (`.for('update')`), checks the outstanding amount and increments `amount_paid` with ``sql`amount_paid + ${amount}` ``. In Drizzle this reads like the SQL a reviewer would write, in one API. In Prisma 7 the locking part would be raw SQL or TypedSQL next to ORM calls; in Prisma 8 it moves to the new query builder, which was still a release candidate.
4. **Types without a generate step.** Types are inferred from `pgTable` definitions, so `packages/contracts` and the API cannot fall out of sync with the schema between `prisma generate` runs (Prisma 7).
5. **Thin runtime.** Drizzle adds little over node-postgres, which matters for many short transactions during month-end. Prisma 7 closed most of this gap by dropping the Rust engine binary, so this is a minor point now, not a deciding one.

## Advantages

- One TypeScript source for tables, constraints, indexes and RLS, close to `schema.sql`.
- Easy to read SQL for locking and aggregate queries; `EXPLAIN` output maps directly to code.
- Works unchanged behind PgBouncer in transaction mode, because tenant context is transaction-local.

## Disadvantages

- Drizzle releases have introduced breaking changes; we must pin versions and read changelogs.
- No equivalent of Prisma 7's nested-write API; inserting a document with its lines is explicit code.
- drizzle-kit does not generate partitioning, so `audit_logs` partitions are custom SQL plus a monthly maintenance job.

## Trade-offs accepted

- We accept a less polished developer experience than Prisma 7, and a smaller ecosystem, in exchange for schema-level visibility of every constraint the business relies on.
- We accept writing some SQL by hand; for financial code we consider that an advantage.

## Consequences / follow-ups

- A lint rule forbids importing the root `db` handle in repositories; only the `tx` from `withTenantTx` can be used, so no query runs without tenant context.
- CI runs `drizzle-kit generate` and fails if the generated migration differs from the committed one (schema drift check), plus a migration dry run against Testcontainers PostgreSQL.
- Migrations follow expand/contract so the previous release keeps working during deploy (ADR-012).
- **Revisit when:** Drizzle stops shipping fixes for our PostgreSQL features, or a breaking release would cost more than about a sprint to adopt; or Prisma 8 has been generally available for about two quarters with its RLS, CHECK and locking support proven in production. Because `schema.sql` is plain SQL, a move to Kysely or Prisma stays possible without changing the database.
